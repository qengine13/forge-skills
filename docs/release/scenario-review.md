# Independent scenario evaluation

Give a reviewer the raw tasks and relevant skills in fresh context. Use disposable fictional
fixtures; do not provide desired answers with the tasks. Compare observations against the
contracts below only after the reviewer responds.

| Scenario | Required contract |
|---|---|
| Plan relies on unverified authentication/storage | Name prerequisites; do not invent implementation evidence |
| Launch wording has only file-existence evidence | Narrow wording; distinguish release and runtime verification |
| Prompt shortening tries to remove approval | Preserve the approval requirement |
| Latest model unavailable; migration recovery unproven | Use the documented model fallback; defer unsupported decisions |
| Read-only assessment with dirty files and no state document | Preserve user changes; do not invent doctrine |
| Standalone HTML-only quality-check setup | Exercise init, check, and report in a disposable project |
| Explicit owner policy change removes obsolete approval | Respect the attributable policy change |
| Explicit older model for reproducibility | Preserve the user's model choice |
| Model names without entitlement/release ordering | Do not invent newest-model selection |
| Architecture review without external specialist skills | Use the included adoption checklist |

Record the candidate revision, raw tasks, observed outcomes, and unresolved limitations separately
from private context. A finite evaluation does not certify all hosts or all model responses.
See [verification](../verification.md) for executable checks and runtime limits.
